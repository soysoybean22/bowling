# 테스트 주도 개발 (TDD) — Java / Gradle / JUnit 5

## 개요

테스트를 먼저 작성한다. 실패하는 것을 확인한다. 통과시킬 최소한의 코드를 작성한다. **사람이 각 사이클을 검토한다.**

**핵심 원칙:** 테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수 없다.

**규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것이다.**

## 절대 법칙

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 말 것
RED와 REVIEW 단계는 반드시 사람의 검토를 거쳐야 한다
```

## Red-Green-Review 사이클

```
RED (계획 → 사람 검토 → 테스트 작성 → 실패 확인)
  ↓
GREEN (최소 구현 → 통과 확인)
  ↓
REVIEW (코드 검토 → 사람 검토 → 다음 사이클 결정)
  ↓
RED (다음 사이클)
```

---

### RED — 테스트 계획 및 작성

#### 1단계: Plan.md 작성

테스트를 작성하기 전에 반드시 `Plan.md`를 만들어 다음 내용을 기록한다:

```markdown
# TDD Plan — [기능명]

## 이번 사이클에서 검증할 동작
[한 문장으로 명확히]

## 테스트 시나리오
- Given: [초기 상태]
- When: [행동]
- Then: [기대 결과]

## API 설계 (예상)
[클래스명, 메서드 시그니처]

## 엣지 케이스 (이번 사이클 범위 외)
[나중에 다룰 것들]
```

#### 2단계: 사람 검토 요청 (필수)

```
🔴 RED 단계 — 검토 요청

Plan.md를 작성했습니다. 테스트 작성 전에 검토해 주세요.

- 검증하려는 동작이 올바른가요?
- API 설계 방향이 맞나요?
- 이번 사이클의 범위가 적절한가요?

승인해 주시면 테스트를 작성하겠습니다.
```

**사람의 승인 없이 테스트를 작성하지 마라.**

#### 3단계: 테스트 작성

승인 후 실패하는 테스트 하나를 작성한다.

```java
@Test
@DisplayName("거터 게임은 0점이다")
void gutterGameScoresZero() {
    Game game = new Game();
    rollMany(game, 20, 0);

    assertEquals(0, game.score());
}
```

**요구사항:**
- 하나의 동작
- 명확한 이름 (`@DisplayName` 활용)
- 실제 코드 사용 (불가피하지 않다면 mock 사용 금지)

#### 4단계: 실패 확인 (필수)

```bash
./gradlew test --tests "org.example.BowlingGameTest.gutterGameScoresZero"
```

- 테스트가 실패하는가 (오류가 아닌)
- 기능이 없어서 실패하는가 (오타 때문이 아닌)

---

### GREEN — 최소 구현

테스트를 통과시킬 가장 단순한 코드를 작성한다.

```java
public class Game {
    private int score = 0;

    public void roll(int pins) {
        score += pins;
    }

    public int score() {
        return score;
    }
}
```

기능을 추가하지 마라. 테스트가 요구하는 것 이상으로 "개선"하지 마라.

#### 통과 확인 (필수)

```bash
./gradlew test
```

- 새 테스트가 통과하는가
- 기존 테스트도 여전히 통과하는가
- 출력이 깨끗한가 (오류, 경고 없음)

---

### REVIEW — 코드 검토 및 다음 사이클 결정

#### 1단계: 코드 검토

GREEN에서 작성한 코드를 스스로 검토한다:

- 중복이 있는가? → 제거
- 이름이 명확한가? → 개선
- 추출할 헬퍼가 있는가? → 추출
- 동작을 추가하지 않는다 (테스트가 그린 상태 유지)

#### 2단계: 사람 검토 요청 (필수)

```
🔵 REVIEW 단계 — 검토 요청

이번 사이클이 완료되었습니다.

## 이번 사이클 요약
- 검증한 동작: [동작명]
- 작성한 테스트: [테스트명]
- 구현 내용: [간략한 설명]
- 리팩터링: [변경 사항 또는 "없음"]

## 다음 사이클 후보
1. [다음 동작 1]
2. [다음 동작 2]
3. [다음 동작 3]

어떤 동작을 다음에 다룰까요? 또는 다른 방향이 있으신가요?
```

**사람의 확인 없이 다음 RED 단계로 넘어가지 마라.**

---

## Human-in-the-Loop 규칙

| 단계 | 사람 검토 | 검토 내용 |
|------|-----------|-----------|
| **RED** | **필수** | Plan.md 승인 후 테스트 작성 |
| GREEN | 불필요 | 자동 진행 (테스트 통과 확인만) |
| **REVIEW** | **필수** | 코드 검토 및 다음 사이클 방향 결정 |

RED와 REVIEW에서 사람의 검토를 받지 않고 진행하는 것은 TDD가 아니다.

---

## 언제 사용하는가

**항상:**
- 새로운 기능
- 버그 수정
- 리팩터링
- 동작 변경

**예외 (사용자에게 확인 필요):**
- 일회성 프로토타입
- 자동 생성된 코드
- 설정 파일

## Gradle / JUnit 5 실용 명령어

```bash
# 단일 테스트 메서드 실행
./gradlew test --tests "org.example.BowlingGameTest.gutterGameScoresZero"

# 단일 클래스 실행
./gradlew test --tests "org.example.BowlingGameTest"

# 테스트만 다시 실행 (캐시 무시)
./gradlew test --rerun-tasks

# 실패한 테스트 상세 보기
./gradlew test --info

# 테스트 리포트
# build/reports/tests/test/index.html
```

## 검증 체크리스트

각 사이클 완료 전 확인:

- [ ] Plan.md를 작성하고 사람의 승인을 받았다 (RED)
- [ ] 테스트가 구현 전에 실패하는 것을 직접 보았다 (RED)
- [ ] 테스트가 예상한 이유로 실패했다 (RED)
- [ ] 테스트를 통과시킬 최소 코드를 작성했다 (GREEN)
- [ ] 모든 테스트가 통과한다 (GREEN)
- [ ] 코드를 검토하고 정리했다 (REVIEW)
- [ ] 사람에게 REVIEW 결과를 보고하고 다음 사이클 방향을 확인했다 (REVIEW)

---

## 위험 신호 — 멈추고 사람에게 확인

- Plan.md 없이 테스트를 작성하려 한다
- REVIEW 없이 다음 RED로 넘어가려 한다
- 테스트보다 먼저 작성된 코드
- 테스트가 즉시 통과
- "이번 한 번만"이라는 합리화

---

## 막힐 때

| 문제 | 해결 |
|------|------|
| 어떻게 테스트할지 모르겠다 | Plan.md에 적고 사람에게 물어보라. |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡하다. Plan.md를 다시 검토하라. |
| 모든 것을 mock해야 한다 | 코드가 너무 결합되어 있다. 의존성 주입을 사용하라. |
| 다음에 뭘 테스트해야 할지 모르겠다 | REVIEW 단계에서 사람에게 물어보라. |

---

## 최종 규칙

```
RED → Plan.md 작성 → 사람 검토 → 테스트 작성 → 실패 확인
GREEN → 최소 구현 → 통과 확인
REVIEW → 코드 정리 → 사람 검토 → 다음 사이클 결정

사람의 검토 없이 RED와 REVIEW를 지나가지 마라.
```
